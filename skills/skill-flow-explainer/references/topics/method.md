# 从业务到策略
先从输入、任务和最终成果理解业务，再画纵向主线。章节标题和函数名是线索，不自动成为节点。优先尊重源文件明确的业务图；若只存在执行流程，归纳的业务分组标为“分析归纳”。相同输入一次产生多个结果维度，应在同一节点中展开。条件分支写出触发、执行范围及返回点；迭代说明退出条件。

策略回答“如何判断和选择”；工具回答“谁执行”；规则回答“边界和必需条件”；验收回答“怎样知道这一步可靠”。规则的硬性/默认/可选只按原文表达判断。不要替目标补上行业通用理论，也不把自身推荐写成源有能力。

每个节点至少记录目的、输入、产物、策略来源和检查方式。来源可能是入口、知识页、脚本或真实运行记录。正文用大白话，技术细节可展开。知识页面存在不等于会被调用；核对入口、读取触发、返回位置和真实函数调用。目标没有分离流程与策略时如实描述，不先重构再报告。

证据类型 explicit=文档明确规定，code=静态代码可确认，inferred=基于源码归纳，runtime=实际运行记录支持。静态代码不证明实际业务效果，运行记录不证明普遍可靠性。文件名和版本声明不足以证明方法生效。未读取、未找到和未验证分别说明；代码与文档不一致时保留两边证据及影响。

改策略后结果有提升是待验证假设。解释可插拔性时检查输入输出是否稳定、影响范围是否有界、历史是否保留，而非看到 references 文件夹就认定能够自动进化。
